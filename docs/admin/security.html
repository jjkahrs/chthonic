Security behaviour

Sessions (backend-for-frontend)

  • Sign-in goes through auth's /v1/auth/login. The access and refresh tokens are kept only in the chthonic_admin_access / chthonic_admin_refresh cookies: HttpOnly, SameSite=Strict, Path=/api, and Secure unless COOKIE_SECURE=false. The SPA's JavaScript never sees a token.
  • Access tokens are verified locally against auth's JWKS (issuer, audience, expiry). Reads take the role from the token. Every write (any non-GET /api request) and GET /api/session re-check the caller with auth's GET /v1/me and use the role it returns; the answer is cached per access token for 5 seconds, so a role change, ban or account deletion takes effect within 5 seconds. Demoted to player → 403 forbidden and the session is ended as at sign-in; banned or deleted → 401 unauthorized and the cookies are cleared; auth unreachable → 502 auth_unavailable (writes never fall back to the token's role). A session revoke is not seen by /v1/me (access tokens carry no session id): it ends the session at the next refresh, at most 15 minutes later. An expired access token is refreshed through auth once per refresh token, even under parallel requests (auth treats a reused refresh token as theft).
  • Players are refused at sign-in (403) and the session auth just created for them is logged out.
  • Logout calls auth's logout and clears the cookies.

CSRF

Double-submit token: chthonic_admin_csrf (readable by JavaScript, SameSite=Strict, Path=/) is handed out on the first /api request and replaced at sign-in. Every non-GET request must send the same value in X-CSRF-Token, or it gets 403 csrf_invalid.

Online guard and force

Before any character write, the admin service asks the character's realm whether the account is online. Online → 409 character_online, and the UI offers a Kick. If the realm has no admin endpoint, refuses the connection or times out (WORLD_ADMIN_TIMEOUT_MS) → 503 realm_unreachable. Admins may send force: true to write anyway; the audit row records forced=true. GMs cannot force (403).

World admin port

  • TLS to each world server's admin port, verified against WORLD_ADMIN_CA_FILE. The first message carries WORLD_ADMIN_SECRET, which the world compares in constant time. One connection per request.
  • The secret lives only in the environment: never stored, logged or returned.
  • Realm admin hosts and ports are admin-only data. GMs never receive them: their requests use the server-side copy in chthonic_admin.realm_endpoints (see Setup).
  • Never publish the world admin port or the admin app to the internet. Compose keeps 7780 on the compose network and binds 3200 to 127.0.0.1. Auth (whose /v1/admin the admin app calls) is on 127.0.0.1:3100 unless AUTH_BIND opens it; MySQL and Mailpit are loopback only.

Least privilege

  • The admin service never connects to chthonic_auth. Account and realm changes go through auth's API with the caller's token, so auth enforces its own rules (for example GMs only on player accounts, no self-ban).
  • Its world MySQL user has SELECT, UPDATE on chthonic_world.characters only: characters are soft-deleted, never removed.
  • Its admin MySQL user owns chthonic_admin only.

Audit log

Every mutating request writes exactly one admin_audit row before the response: actor id, email and role, action (for example character.rename, account.ban, realm.kick), target, before/after JSON, forced, and result (ok or the error code, including role refusals). Passwords are never recorded. Timestamps are UTC, written by the app.

HTTP hardening

helmet defaults (CSP default-src 'self', no MIME sniffing, no framing), Cache-Control: no-store on /api, a 100 KB JSON body limit, zod validation of every input, and generic 500s that never leak internals.
