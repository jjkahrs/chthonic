Security behaviour

  • No account discovery.
    • register, resend-verification and forgot-password return identical responses for every email.
    • Registering an email that already has an unverified account replaces that account's password with the new one, invalidates every earlier verification link and emails a new one. Only the latest registrant's password works once the inbox owner verifies, so someone who registers a victim's email first can't have the victim verify the attacker's password. A verified account is unchanged; its owner gets a "sign-up attempt" email.
    • Login returns invalid_credentials for both an unknown email and a wrong password. An unknown email still runs a bcrypt comparison, so both cases take about the same time.
    • Emails are sent fire-and-forget, so the time to send an email doesn't show up in response times either.
  • Login check order. Checks run in this order: lockout, password, email verified, ban. email_not_verified and account_banned are only returned once the password is correct.
  • Lockout.
    • Counted per account and client IP (the address the rate limiter uses; see TRUST_PROXY). 5 consecutive wrong passwords from one IP lock the account for 15 minutes for that IP only. While it's locked, even the correct password from that IP gets 423 account_locked (details.lockedUntil); the same account still logs in from any other IP, so a stranger can't lock the owner out.
    • A successful login clears that IP's counter. A password reset and the admin unlock clear every IP's counter and lock.
    • Counters live in the login_failures table. A row with no active lock is deleted once it's a day old (bounded deletes on each failed login), so failures older than a day are forgotten.
    • Trade-off: lockout only happens to accounts that exist, so a client that sends 5 wrong passwords can learn whether that email is registered.
  • Rate limiting.
    • Fixed windows per IP, stored in MySQL, so limits survive restarts and are shared by every instance.
    • Expired rows are deleted on each write.
    • Because the windows are fixed, a client can send up to twice the limit in a short burst across a window boundary.
  • Passwords.
    • Passwords must be 10–128 characters and are hashed with bcrypt at cost 12.
    • bcrypt only reads the first 72 bytes, so each password is first SHA-256 hashed (base64). That way every character of a 128-character password counts.
  • Tokens at rest. Refresh, verification and reset tokens are 256-bit random values. Only their SHA-256 hashes are stored.
  • Refresh rotation.
    • Each refresh consumes the token it was given.
    • Presenting an already-rotated token revokes the whole session (token family).
    • The check is strict: if a client sends two refreshes in parallel with the same token, its session is revoked.
  • Logs never contain passwords, tokens, request bodies or SQL parameters.
  • Published ports. The compose stacks publish MySQL and Mailpit on 127.0.0.1 only: Mailpit has no authentication and shows every reset link, so anyone who reaches it can take over any account. Auth (including /v1/admin) is published on 127.0.0.1 unless AUTH_BIND=0.0.0.0 is set.
  • No placeholder seed admin. Auth refuses to start while SEED_ADMIN_PASSWORD starts with change-me (the .env.example value). Changing .env does not change an admin that was already seeded: change that account's password through forgot-password.
