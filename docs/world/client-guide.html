Client implementer guide

Everything a game client needs to log in, enter the world, move, see others, react to every server message and connect to chat, in any language. It is wire-level and engine-neutral: it says what a client sends and must handle, not how an engine should expose it. The reference pages are Protocol (every message and code), Chat service protocol and Auth endpoints; where this guide and the code disagree, the code wins (world/protocol/messages.h, protocol version 9).

The headless test client world/bot/ (world_client.cpp, auth_client.cpp, scenarios.cpp) is a working reference implementation of everything here. Defaults below are the server's (Configuration); a realm may change them.

End-to-end flow

client               auth (HTTP)                 world server (TLS 7777)            chat service (TLS 7778)
  |-- POST /v1/auth/login ------>|                           |                                   |
  |<- {accessToken, refreshToken}|                           |                                   |
  |-- GET /v1/realms (Bearer) --->|                           |                                   |
  |<- {realms: [{host, port,..}]}|                           |                                   |
  |-- TCP + TLS to realm host:port ------------------------>|                                   |
  |-- Hello{9}, Auth{accessToken} ------------------------->|                                   |
  |<- AuthOk ------------------------------------------------|   lobby                           |
  |-- CharListReq / CharCreate / CharDelete --------------->|                                   |
  |-- EnterWorld{charId} ---------------------------------->|                                   |
  |<- EnterWorldOk, ChatServer{host, port} -----------------|   in world                        |
  |-- TCP + TLS to ChatServer host:port --------------------------------------------------------->|
  |-- Hello{9}, Auth{accessToken} --------------------------------------------------------------->|
  |<- AuthOk, ChatChannel{1, General, joined} -----------------------------------------------------|

1. Log in to auth

  • Request: POST /v1/auth/login, JSON body {"email": "...", "password": "..."} (no auth header). Dev stack: http://localhost:3100.
  • Response 200: {tokenType: "Bearer", accessToken, expiresIn, accessTokenExpiresAt, refreshToken, refreshTokenExpiresAt} (auth/src/services/auth.ts). expiresIn is the access token's lifetime in seconds (ACCESS_TOKEN_TTL_SECONDS, default 900).
  • Errors: 401 invalid_credentials, 403 email_not_verified or account_banned, 423 account_locked, 429 rate_limited (with Retry-After); shape {"error": {"code", "message", "details"?}} (Auth errors).
  • Refresh: POST /v1/auth/refresh with {"refreshToken": "..."} returns a new pair; the old refresh token is consumed. Account registration, verification and password reset are in Auth endpoints.

2. Pick a realm

  • Request: GET /v1/realms with header Authorization: Bearer <accessToken>.
  • Response 200: {realms: [{id, name, host, port, region, status, sortOrder}, ...]}, ordered by sortOrder, then id (auth/src/repositories/realms.ts). host / port are where that realm's world server accepts game clients: this is how a client finds the world server. status is online, offline or maintenance, as an admin set it; the world server does not update it and does not check it, so it is only advice for the realm picker.
  • Dev stack: the compose setup seeds realm REALM_ID (1) as Local, 127.0.0.1:7777, online (world/docker/admin-db-init.sh).

3. Token for the world server

  • Which token: the access token (a JWT, RS256), sent as Auth.accessToken. It is not bound to a realm; the world server checks its signature against auth's JWKS, iss (JWT_ISSUER), aud (JWT_AUDIENCE), exp (with JWT_CLOCK_SKEW_SECONDS leeway), a numeric sub (the account id) and a role claim (Security).
  • Checked once: only at the handshake. A connected session stays up after the token expires, so connect with a token that has time left, and refresh it before connecting again or before opening the chat connection if it is close to accessTokenExpiresAt.

4. Chat

  • Where: right after EnterWorldOk the world server sends ChatServer{host, port} (only when the realm sets CHAT_PUBLIC_HOST; without it there is no chat service to use).
  • Connect: a second TLS connection there, the same frames, Hello{9} and Auth with a valid access token of the same account. The chat service holds the AuthOk until the world server has reported the account's character as online (up to CHAT_BIND_TIMEOUT_MS, default 5 s, then Disconnect{no_character}), then sends AuthOk and ChatChannel{1, "General", 1} (the first CHAT_CHANNELS entry).
  • Messages a client handles there: ChatLine, ChatChannel, ChatNotice, Ping, Disconnect; it sends ChatSend, ChatJoin, ChatLeave, ChatIgnore, ChatMute (GM / admin) and Pong. Payloads in Chat service messages; rules, notices and limits in Chat service protocol.
  • Lifetime: the chat connection is closed with Disconnect{no_character} when the character leaves the world or the world server's link to chat drops; a second chat connection for the account closes the first with logged_in_elsewhere. Say, yell and emote stay on the world connection (Say / ChatMsg) either way.

Transport

  • TLS over TCP: TLS 1.2 or later (the server disables SSLv2/3, TLS 1.0 and 1.1). Default world port 7777, chat 7778. The server sends no TLS close_notify when it closes (world/server/net/session.cpp): treat an EOF or a TLS "unexpected EOF" after a Disconnect, or at any time, as the connection closing.
  • Dev certificate: with no TLS_CERT_FILE, the world server makes a self-signed EC P-256 certificate TLS_DEV_CERT_DIR/server.crt (compose: /app/certs/server.crt in volume world-certs), SANs localhost, world, chat, 127.0.0.1, with CA:TRUE. The chat service presents the same certificate in the dev stack. Trust it by loading that file as the client's only CA and verify the host name you connected to (as the bot does with --ca). Do not turn verification off.
  • TCP_NODELAY is recommended: the server sets it on its side; messages are small.

Frame

+----------------+----------------+----------------------+
| u16 length     | u16 opcode     | payload (length B)   |
+----------------+----------------+----------------------+
  • length counts the payload only, not the 4-byte header. Frames follow each other back to back on the TLS stream; one read may hold several frames or part of one. Read 4 bytes, then exactly length more.
  • Little-endian everywhere.

Field types

TypeEncoding
u8 / u16 / u32 / u64Unsigned, little-endian
f32IEEE-754 single precision, as its u32 bits. NaN and infinity are malformed (both directions)
stru16 byte length, then that many bytes (no terminator; UTF-8 where noted)
vec3f32 x, f32 y, f32 z; metres, y up, x/z the ground plane
optionsu8 count, then count × (str key, str value); keys unique (the server writes them in ascending byte order)
CharInfou64 id, str name, vec3 pos, options
bool fieldsu8, 0 or 1; any other value is malformed

Heading is radians, atan2(dx, dz): 0 faces +z (Protocol, Maps).

Size limits per direction

  • Client to server: a frame whose length is over MAX_FRAME_BYTES (default 4096, settable 64–65535) is answered Disconnect{frame_too_large}, decided from the header alone. The chat service has its own MAX_FRAME_BYTES (default 4096). Valid client messages fit the default easily: the largest are Auth (a JWT, typically under 1 KB) and a full ClientEvent (at most 2 + 32 + 2 + 1024 + 4 = 1064 payload bytes).
  • Server to client: up to the u16 limit, 65535 payload bytes (kMaxPayloadBytes). MAX_FRAME_BYTES does not apply: an EntityMoves with 3276 entries is 65522 bytes, and a ComponentUpdate, ServerEvent or Reply may be just as big. A client must accept every frame up to 65535 payload bytes.

Exact-decode rule

A payload must decode to exactly length bytes (world/protocol/codec.cpp decode_as): a short field, a string that runs past the end, trailing bytes, a non-finite float or an out-of-range enum or bool are malformed. The server disconnects a client that sends one (Disconnect{malformed}), and an opcode it does not know with Disconnect{unknown_opcode}. A client should apply the same rule to what it receives; the reference client closes the connection on an undecodable frame.

Connection state machine

             TCP connect
 [closed] ---------------> [tls] --TLS ok--> [handshake] --AuthOk--> [lobby] --EnterWorldOk--> [world]
    ^                        |                   |                       |                      |   ^
    |                        | TLS fails /       | Disconnect{...} /     |                      |   | MapChange
    |                        | deadline: closed  | handshake_timeout     |                      +---+ (stays in world)
    |                        v                   v                       v                      v
    +------------------- EOF / Disconnect{reason} from any state (then the server closes) ---------+

There is no message to leave the world or go back to the lobby: to log out or switch characters, close the connection and connect again. The server keeps an internal "verifying" phase while it checks the token; for a client it is part of the handshake.

In every state an undecodable frame is malformed, an unknown opcode unknown_opcode, an oversized header frame_too_large, and a flood rate_limited (below). Source: world/server/app/game_server.cpp on_message, handle_lobby, handle_world; world/server/net/session.cpp handle_frames, deliver.

Timeouts

  • Handshake: HANDSHAKE_TIMEOUT_MS (default 10 s) from the moment the server accepted the TCP connection until it sends AuthOk, covering TLS, Hello, Auth and the token check. Missed: Disconnect{handshake_timeout}, or a plain close if TLS never finished. The chat service adds its bind wait: HANDSHAKE_TIMEOUT_MS + CHAT_BIND_TIMEOUT_MS.
  • Idle: a connection from which the server has received no frame (any frame, a Pong included) for more than IDLE_TIMEOUT_MS (default 60 s) gets Disconnect{idle_timeout}. The server checks at each heartbeat, so it can take up to one ping interval longer.
  • After a Disconnect: the server stops reading, sends nothing more and closes once the frame is written, or after 2 s.

Heartbeat

  • Server pings: from the end of the TLS handshake, every min(PING_INTERVAL_MS, IDLE_TIMEOUT_MS) (default 20 s) the server sends Ping{nonce} (nonce counting from 1). The client must answer Pong{same nonce} promptly, in any state; the server does not check the nonce, but the Pong is what keeps an otherwise silent client from going idle.
  • Client pings: optional. The server answers every Ping with Pong{nonce} in any state, even before Hello; a client can use that to measure round-trip time. A Pong the client sends is otherwise ignored.

Rate limits

  • Per connection: a token bucket of MSG_RATE_PER_SEC (default 60) messages per second, bursts up to MSG_BURST (default 120), counting every frame (Ping and Pong too). Frames over the limit are dropped without a word (a dropped Ping gets no Pong); still over after MSG_RATE_GRACE_MS (default 2 s) without regaining headroom: Disconnect{rate_limited}. Chat service defaults: 20 per second, burst 40. Sending Move once per server tick (20 Hz) leaves plenty of room.
  • Per message type: one character request in flight; Say CHAT_RATE_COUNT per CHAT_RATE_WINDOW_MS (5 per 10 s); ClientEvent 10 per 1 s per character; see each message below.
  • Send buffer: a client that stops reading until more than MAX_SEND_BUFFER_BYTES (1 MiB) is queued for it is closed without a Disconnect.

MapChange (portal, script, instance copy)

client                                        world server
  |---- Move{.., epoch 1} -------------------->|  walks into a portal area: accepted
  |<--- [ServerEvent x n] ----------------------|  what the old map's Lua sent in onMapLeave (other maps only)
  |<--- MapChange{map, pos, heading, epoch 2} -|  drop every remote entity; load map if it changed
  |<--- Despawn x n ----------------------------|  one per old neighbour (already dropped: ignore)
  |---- Move{.., epoch 1} (in flight) -------->|  older epoch: dropped silently
  |<--- Spawn x n -------------------------------|  the new neighbours, from the next AOI pass (this tick or the next)
  |<--- ComponentUpdate x n --------------------|  their aoi components
  |---- Move{.., epoch 2} -------------------->|  from mc.pos; the speed budget starts empty again
  • Instance copies and layers: every copy of an instance map (and every layer of a layered map) has the map's id, so moving into one, or between two copies of the same map, is a MapChange whose map may equal the current one. Keep the map loaded, place yourself again, and let the Despawns and Spawns swap the entities. The wire never names the copy.
  • Refused transfers (copy full, layer full or gone) send the client nothing from the engine; the game's Lua may tell it (the sample test hook sends test.instance_full, catalog).
  • Your entity id stays the same across a MapChange, and so do your own replicated components (they are not resent).

Server-to-client messages

Order within a tick

The world sends from one game thread, and every connection's frames go out in the order they were sent (session.cpp Inbox), so these orders hold on the wire. Each 50 ms tick (TICK_HZ 20) sends, per player, in this order (world.cpp World::tick, map_context.cpp tick_move / tick_rest):

  1. Correction (movement), then for a portal on the same map MapChange + Despawns;
  2. a portal onto another map: ServerEvents from onMapLeave, then MapChange + Despawns;
  3. Spawn / Despawn (AOI);
  4. ChatMsg / ChatNotice (proximity chat);
  5. during the Lua update: Despawns of NPCs it destroys, MapChange + Despawns of its same-map transfers;
  6. EntityMoves;
  7. ComponentUpdate / ComponentRemove;
  8. ServerEvent / Reply, in the order the Lua queued them;
  9. end of tick: Lua transfers onto other maps (as step 2), and broadcast events from other maps.

Between ticks, as messages and disconnects arrive: the lobby answers, EnterWorldOk + ChatServer, and a leaving player's onLeave ServerEvents followed by its Despawn to everyone who saw it. Ping / Pong can come between any two messages.

Guarantees that follow: AuthOk before any lobby answer; EnterWorldOk before anything about the world; an entity's Spawn before any EntityMoves entry or ComponentUpdate for it, and nothing about it after its Despawn until a new Spawn; MapChange before the Despawns of the old neighbours and the Spawns of the new ones; a tick's ServerEvents after its component replication; a leaver's onLeave events before its Despawn; Disconnect last. broadcast payloads are the exception: they reach players on every map, so they can name entities the receiver has never seen.

Client prediction

  • seq: number every Move of the connection 1, 2, 3, ... and never reset it (not on Correction or MapChange). The server does not check it; it only echoes the rejected one as Correction.ackSeq.
  • epoch: 0 after EnterWorldOk; then always the epoch of the last Correction or MapChange received. The server drops, without a Correction, every Move whose epoch is lower than its own (sent before the client heard of the correction or the move). A client that never adopts the new epoch has every later move dropped and stands still on the server.
  • Validation (world/server/world/systems.cpp movement_system, world/server/world/rules.cpp validate_move), on the next tick, for every queued Move in arrival order:
    1. older epoch: skipped silently;
    2. movement locked by the server's Lua (chthonic.setMovable): rejected;
    3. x/z not on a tile the map declares: rejected;
    4. speed: the x/z distance from the last accepted position must fit the budget, which refills at MAX_SPEED + SPEED_TOLERANCE (10 + 1 m/s) of server time, up to MOVE_BURST_SECONDS (1 s) of travel (11 m), and starts empty at EnterWorldOk and at every MapChange; y does not count;
    5. air: ending more than MOVE_MAX_AIR (6 m) above the ground under the new x/z while not descending: rejected (falling is always allowed);
    6. navmesh: on a map with one and MOVE_NAV_CHECK on, the end point must be on it: rejected otherwise;
    7. accepted: y more than MOVE_GROUND_TOLERANCE (0.5 m) under the ground is lifted onto it, then clamped to [MIN_Y, MAX_Y]. This adjustment is not reported back to the mover; observers see the adjusted y.
    The first rejection in a tick ends that tick's batch: the moves after it are discarded, and one Correction{last accepted position, ackSeq = rejected seq, epoch + 1} goes out. heading is taken as sent.
  • Accepted moves are not acknowledged. A client knows a move was accepted only because no Correction named it.
  • Rate: one Move per tick (every 50 ms) when the player moves is enough; more is allowed (they are all checked in the next tick) but counts toward the message rate.

seq = 0; epoch = 0; pos; heading
budget = 0; lastRefill = now()          // optional mirror of the server's budget
history = []                             // optional: inputs since the last Correction, for replay

on EnterWorldOk(m):  pos = m.pos; heading = m.heading; epoch = 0; budget = 0; history = []
on MapChange(mc):    dropRemoteEntities(); if mc.map != currentMap then loadMap(mc.map)
                     pos = mc.pos; heading = mc.heading; epoch = mc.epoch; budget = 0; history = []
on Correction(c):    pos = c.pos; epoch = c.epoch
                     // every move with seq >= c.ackSeq was discarded; every earlier one is part of c.pos
                     history = []        // or: re-simulate inputs newer than c.ackSeq from c.pos and send them as new Moves

every frame:
    next = simulate(pos, input, dt)      // keep x/z speed at or below MAX_SPEED, y on the ground (maps.html#ground)
    if sendTimer >= 50 ms and next != lastSent:
        seq = seq + 1
        send Move{pos = next, heading, clientTimeMs = nowMs() mod 2^32, seq, epoch}
        history.append({seq, input}); lastSent = next
    pos = next

Entities

  • entityId (u32) names a player character or NPC while it is in the world. It is unique among the realm's live entities on every map, and yours (EnterWorldOk.entityId) stays the same across MapChanges. Treat an id as valid only from its Spawn to its Despawn: once an entity is gone, a later entity may get the same number (the server reuses freed slots), and every login creates a new entity, so never carry an id over to another connection.
  • You are never spawned to yourself: no Spawn, Despawn or EntityMoves entry ever carries your own id. Your position is yours, corrected by Correction and MapChange; your components arrive as ComponentUpdates with your id.
  • Spawn.kind: 0 a player (name the character's name, template empty); 1 an NPC (name its definition's name, e.g. Guard, template the name of the client-side look the game chose, e.g. Guard; how a client maps a template to a model is the client's).
  • AOI: a player sees every other player and NPC in the same map context (the same map, and the same instance copy or layer) within AOI_VIEW_RADIUS (128 m) on x/z. The view is recomputed each tick; whoever entered gets a Spawn, whoever left a Despawn. Range is symmetric. NPCs see nothing.
  • EntityMoves: one per tick per viewer, holding every entity it sees that moved that tick (players' accepted moves and NPC moves the Lua made); an entity that stands still sends nothing. More than 3276 entries come as several EntityMoves in a row in the same tick. No timestamps: positions are 20 Hz samples, so interpolate between them (for example, render about two ticks behind).
  • Entity state a client keeps: {id, kind, name, template, pos, heading, components{name: json}}, created by Spawn, updated by EntityMoves / ComponentUpdate / ComponentRemove, removed by Despawn or MapChange.

Lua-driven content

Components, events and interactables are defined by the game's server Lua (Lua components and systems); the engine only carries them. A client must handle the messages for any names, and act on the names its game defines.

ComponentUpdate / ComponentRemove

  • Value: the component's full value as a JSON object, canonical encoding: fields in definition order, floats as the shortest decimal that reads back as the same f32 (whole floats keep .0, e.g. 100.0), ints as integers, bools, strings, vec3 / quat as [x, y, z] / [x, y, z, w], enums by name, arrays as arrays. Replace the stored value; never merge.
  • Who gets it (the definition's replicate): owner: only the owning player's client (an NPC's: nobody); aoi: the owner and every client that sees the entity; none: never sent.
  • When: at most one per component per tick, after the Lua update, only when the value differs from what was last sent. The owner gets every replicated component it has on its first tick in the world. A viewer gets all of an entity's aoi components on the tick the entity came into view, after its Spawn.
  • Not sent: a ComponentRemove on Despawn or MapChange (drop the entity's components yourself), and a component whose frame would pass 65535 bytes (the server logs it and skips it until it fits).
  • Server-authoritative: a client never sends these; doing so is Disconnect{unexpected_message}. Ask for changes with a ClientEvent.

ServerEvent

  • name: any non-empty string the Lua chose (not limited to the ClientEvent name rules). json: any JSON value, compact, null when the Lua sent none; object keys in byte order; bytes that are not UTF-8 replaced with U+FFFD.
  • Audience: sendTo(e): e's client; sendNearby(e): e's client and every client that sees e; broadcast: every player in the world on every map (its own map's with that tick's events, the others' at the end of the tick). Taken when the event goes out: a character that left meanwhile gets nothing.
  • When: after that tick's component replication, so a client already has the Spawn and latest components of an entity the event names (except in broadcasts, see order); events sent from onEnter go out on the next tick, from onLeave before the leaver's Despawn.

ClientEvent and Reply

  • Send: ClientEvent{name, json, requestId}. The JSON is a single object of at most 1024 bytes; build it with a JSON encoder. The server's Lua receives {entity = your entity, data = the object} (plus requestId when it is not 0) on the next tick, in arrival order, and must treat data as untrusted.
  • Requests: pick a non-zero requestId unique among your pending ones (a counter from 1). The server keeps no record of requests: a Reply comes only if a handler calls chthonic.reply, nothing stops a handler from replying twice, and a dropped (rate-limited) event or a handler that never answers produces no Reply. Use a client-side timeout. A Reply reaches you only while you are still in the map context that got the event.
  • Reply.json: ok 1: the data (a JSON value; {} when the handler gave none); ok 0: a JSON string, the reason, e.g. "not enough gold".

Interact

Interact{objectId}: the id of an interactable in the map's objects/<tx>_<tz>.json (Maps, Objects). The client should check the range itself (horizontal distance to the shape's edge at most the object's range, default 3 m); the server checks the map and the range on the next tick and, if both pass, publishes the object's event to the Lua. Nothing comes back from the engine, accepted or not; whatever the game's Lua sends is the answer.

Implementation checklist

The minimum to log in, enter the world, move and see others:

  1. HTTP: POST /v1/auth/login → accessToken; GET /v1/realms with Authorization: Bearer → a realm's host / port.
  2. TLS client with certificate and host name verification (dev: trust server.crt as the CA).
  3. Frame reader / writer: 4-byte header, little-endian, str as u16 length + bytes, finite f32s; accept server payloads up to 65535 bytes; reject undecodable frames.
  4. Send Hello{9} and Auth{accessToken}; wait for AuthOk or Disconnect.
  5. Answer every Ping with Pong{nonce}, in every state.
  6. Lobby: CharListReq → CharList; if empty, CharCreate → CharCreated; then EnterWorld → EnterWorldOk; one request at a time; handle CharError.
  7. World: remember your entityId, load map, place yourself.
  8. Entities: Spawn creates, EntityMoves moves (interpolate), Despawn removes (ignore unknown ids).
  9. Movement: Move at most once per 50 ms while moving, at or below 10 m/s, seq counting from 1, epoch from the last Correction / MapChange; on Correction snap and adopt the epoch.
  10. MapChange: drop remote entities, load the map if it changed, place yourself, adopt the epoch.
  11. Disconnect: show the reason (table); treat EOF as a close.
  12. Tolerate the rest: parse and ignore (or show) ChatMsg, ChatServer, ChatNotice, ComponentUpdate, ComponentRemove, ServerEvent, Reply. None of them needs an answer.
