Maps

The world is a set of maps (continents, dungeons), all run by this one process. A map is seamless inside; maps are joined only by transfers. Players and NPCs on different maps never see each other, even at the same x/z.

<MAP_ROOT>/<folder>/map.json        one folder per map; dot-folders (.server/) are skipped
<MAP_ROOT>/<folder>/areas.json      optional: the map's named areas (see Areas)
<MAP_ROOT>/<folder>/zones.json      optional, client and map tools: the map's zones (see Zones; the server ignores it)
<MAP_ROOT>/<folder>/heights/<tx>_<tz>.r16|.png   optional: tile heightmaps (see Ground)
<MAP_ROOT>/<folder>/.server/spawns/<tx>_<tz>.json   optional, server only: the NPCs a tile places (see NPC spawns)
<MAP_ROOT>/<folder>/.server/nav/<tx>_<tz>.navtile   optional, server only: the tile's baked navmesh (see Navmesh)
<MAP_ROOT>/<folder>/objects/<tx>_<tz>.json   optional, client and chthonic_mapbake: the tile's map objects (see Objects)
<MAP_ROOT>/<folder>/.server/interactables/<tx>_<tz>.json   optional, server only: its interactables (see Objects)

{ "version": 1, "id": 1, "name": "Eastlands",
  "tiles": [[0, 0, 7, 7]],
  "heightRange": [-100, 500],
  "spawn": {"pos": [1024, 0, 1024], "heading": 0},
  "material": "materials/terrain_grass.mat",
  "nav": {"agentRadius": 0.4, "agentHeight": 1.8, "maxClimb": 0.5, "maxSlopeDeg": 45, "cellSize": 0.5} }

A map is a world map (the default: one context for everyone; with layerCap, one per layer) or, with "type": "instance", an instance map, run as one copy per instance key, with maxPlayers, emptyTimeoutSec and a required exit.

  • Tiles: a map is made of 256 m tiles; tile (tx, tz) = (floor(x / 256), floor(z / 256)), so x = 256 is tile 1. The map's origin is the corner of tile (0, 0). tiles lists inclusive rectangles [x0, z0, x1, z1]; the map is their union, and negative tiles are fine.
  • Identity: id (0-65535) is what the database, the wire and Lua use. It must be unique across maps; the folder name only locates the files. version must be 1.
  • Required: version, id, tiles and spawn.pos (on a declared tile). name, spawn.heading, heightRange, material, terrainUv ("tiled" or "map"; anything else fails the map), nav and type ("world" or "instance", with the instance fields, which on a world map fail it) and layerCap (world maps only, Layers) are optional, and unknown keys (such as a map editor's terrainColors) are ignored. The game client's terrain uses heightRange, material, terrainUv and nav.maxSlopeDeg; the server uses heightRange and the heightmaps for the ground. map/heights.h (heightmap decoding and the shared ground triangles) is part of chthonic_map, so the server build needs vcpkg's stb.
  • Startup: every map is loaded and logged (maps loaded). Any bad manifest (with the file and the problem, such as maps/cave/map.json: tiles[0]: x0 <= x1 and z0 <= z1 required), a duplicate id, no maps, a missing START_MAP or one that is an instance map, an instance map's exit off a loaded world map's tiles or in a portal there, a spawn y outside MIN_Y/MAX_Y, or a bad interactables file refuses the start.
  • Bounds: a move onto a tile the map does not declare is rejected with Correction.
  • Characters: characters.map_id (migrations/003_character_map.sql) is saved with the position. On enter, a map that is no longer loaded, or a position no longer on its map, puts the character at START_MAP's spawn (logged). Rows from before the migration have map_id 0, read as START_MAP with their position kept. On an instance map, characters.instance_id names the copy: a live one with room is rejoined, else the map's exit (Instances).
  • Transfers: World::transfer(e, {map, pos, heading}) (and chthonic.transfer from Lua) is the only way to change map, for players and NPCs alike, and also teleports within a map. It moves the entity at once, resets a player's move budget and sends it MapChange, then Despawn for its old neighbours, who get its Despawn. The next interest pass sends the Spawns at the destination: in the same tick for a portal, the next tick for chthonic.transfer. So MapChange always reaches the client first (protocol). Onto another map the entity changes context: a portal moves it at the serial point right after movement, a chthonic.transfer at the end of the tick.
  • Ownership: a transfer to a tile this process does not own is refused and logged. Every loaded tile is owned for now; the check is the seam for running maps in several processes later.

Zones

A zone is a named set of a map's tiles: every declared tile is in exactly one zone, and a zone's tiles are contiguous (connected through shared edges; tiles touching only at a corner are not). Crossing from one zone to the next is seamless: same map, same context, no transfer. zones.json is optional:

{ "version": 1, "zones": [
  {"id": "eastvale", "name": "Eastvale", "tiles": [[0, 0, 3, 7]], "flags": {"pvp": false}},
  {"id": "westmarch", "tiles": [[4, 0, 7, 7]]}
]}
  • Fields: id (required, unique; letters, digits, _ and -, not starting with -, like a map folder), name (defaults to id), tiles (required, inclusive rectangles [x0, z0, x1, z1] like map.json's; the zone is their union) and flags (optional object, passed through untouched). Unknown keys are kept by tools that save the file.
  • No file: the map is one implicit zone: id = the map's folder, name = the map's name (or the folder), every declared tile.
  • Checks: chthonic::map::parse_zones (map/zones.h in chthonic_map) rejects, with the file and zone (maps/vale/zones.json: zone "a": not contiguous (tile 2_0 ...)): bad JSON or fields, a duplicate or badly formed id, a zone with no tiles, a zone tile not declared in map.json, two zones on one tile, a declared tile in no zone, and a zone in pieces. validate_zones runs the same checks on an in-memory zone set and lists every problem; zone_at finds the zone of a tile or a world x, z.
  • Server: the world server and chthonic_mapbake never read zones.json (a bad one does not stop the server); the parser is in the shared library for clients and map tools. The client streams each zone's scene and publishes zone.left / zone.entered locally; there is no server zone tracking.

Map contexts

Like AzerothCore's one Map object per map, each map in use runs in its own context, and one realm context runs what belongs to no map. Contexts are updated one after another on the tick thread, or at once on MAP_THREADS workers (Threading), and meet only at serial points.

  • A map context owns: a registry (every player and NPC on the map), an AOI grid, a Lua state (npcs/ and systems/, every init run when the context starts), the spawner and tile activation, an event bus, and the inbound queues of its players (moves, chat, client events, interacts). The maps' immutable data (manifests, areas, ground, navmesh, objects, spawn files) is loaded once and shared read-only, never copied per context.
  • When: START_MAP's context starts with the scripts, at startup; any other map's the first time it is used (a login or a transfer onto it, an NPC created there, a chthonic.world.post to it), as AzerothCore creates a map on demand. A map's context then stays for the life of the process, like its tiles. Each logs map context started {map, name} at debug level, and the realm realm context started.
  • The realm context: one per process. Its Lua state loads only fsms/ and runs the game machines (GAME_STATE_MACHINES); no map context starts them (State machines). Its bus gets the game machines' fsm.changed (passed on to every map's bus for its next drain) and posts to "realm" and "all". It has no systems: only server C++ subscribes there.
  • Isolation: while a context is updated it touches no other context: chthonic.query, chthonic.get and the rest see its own map's entities only. What reaches past its map is queued for the next serial point: a transfer onto another map (a portal or chthonic.transfer), chthonic.create onto another map, a destroyed NPC whose spawn file is another map's (it respawns there), chthonic.world.post, a game machine change, and a chthonic.broadcast's copy for the other maps' players.
  • Serial points: each tick runs: the realm's bus drain; a serial point (whatever C++ calls queued since the last tick); movement and areas for every map; a serial point (portals onto another map, so the destination's interest pass sends their Spawns this tick); the rest of the tick for every map; a serial point (Lua's transfers, creates and game machine changes; posts go onto their targets' buses here, for the next tick). Maps go in id order. A serial point does what was queued before it began; what that queues waits for the next. Every World call from server C++ (a login, a logout, World::transfer) is one too.
  • Transfer onto another map, at a serial point, in this order: onMapLeave(e) in the old context's systems (and the client events queued there so far are sent); MapChange, the Despawn of each old neighbour, theirs of it and area.leave on the old map's bus; every component moved to the new context (the C++ ones and every Lua component, persisted or not; a StateMachine keeps its current state; the entity id stays); area.enter on the new map's bus; onMapEnter(e, carried) in the new context's systems (Lua). A portal's Spawns and area events come in the portal tick, a chthonic.transfer's in the next. Within a map a transfer is done at once, as before.
  • Entity ids: one process-wide index space, handed to the contexts in blocks (4096 ids for a world map, 256 for an instance copy); a context hands out the ids it freed first (the last freed first, its version bumped) and then new ones from its block, so an id (the entity id on the wire and in Lua) is unique across contexts and an entity keeps it when it changes context. The ids a context gets depend only on what it did itself. With one context they are those a single registry would give. MAX_NPCS counts the NPCs of every context (Threading: how it is shared).
  • Sessions: a player's Move, Say, ClientEvent and Interact go to the context its character is in now.

Threading

Like AzerothCore's MapUpdater (CONFIG_NUMTHREADS), MAP_THREADS (default 1, Configuration) workers update the map contexts at once.

  • MAP_THREADS=1: no workers; every context updates on the tick thread, one after another in map id order.
  • MAP_THREADS=N, N > 1: N workers start with the server and stop at shutdown. Each tick has two update steps (movement and areas; the rest of the tick). In each, every map context is one job; the workers take the jobs in turn and the tick thread waits for all of them (a barrier) before the serial point that follows. The serial points, the realm context, logins, logouts and everything else outside the two steps stay on the tick thread. One map never splits across workers: a single busy map is no faster than with one thread.
  • Same result: with any MAP_THREADS the server sends every session the same messages, in the same order, and saves the same, as with 1 (checkParallelDifferential, Tests). During a step a context touches only its own data:
    • Its sends and saves wait in the context; after the barrier they go out context by context in map id order. A session is in one context, so it gets its messages in the serial order; the network and the DB worker only ever see the tick thread.
    • Entity ids come from the context's own freed ids and block (above). Each context gets a spare block before each step, in map id order, so a step can make a block of new ids (4096 on a world map) without asking anyone; past that it takes a block mid-step (unique ids still, but then which block may vary with timing).
    • MAX_NPCS: before each step what is left under the limit is split evenly among the contexts (map id order takes the remainder). A context may create up to its share; it never takes another's, so the limit holds and what a context may create does not depend on the others' timing. With one map that is exactly the old count. With several, a map can be refused an NPC while the others' shares are unused; the shares are recomputed before every step.
    • Logging is thread-safe, the Lua script deadline is per thread, the maps' data is read only, and a navmesh path search (chthonic.map.path may ask for another map's) takes that map's lock.
  • C++ subscribers on a map's bus (World::bus(map)) run on whichever worker updates that map; the realm's bus stays on the tick thread.
  • Cost: the tick stats lines show each context's update time (Operations). The bench map_threads_bench (4 maps of 100 moving players and 100 Guards) runs a tick in under 40% of the 1-thread time with 4.

Layers

Like WoW's layering or GW2's overflow, a crowded world map can run as several copies, layers, each holding at most layerCap players, so no copy gets crowded (interest management costs about players × players in view). Players in different layers of a map never see or hear each other; everything else about the map is the same.

{ "version": 1, "id": 1, "name": "Eastlands", "tiles": [[0, 0, 7, 7]],
  "spawn": {"pos": [1024, 0, 1024]},
  "layerCap": 500, "emptyTimeoutSec": 300 }
  • layerCap: optional, world maps only, an integer ≥ 1: players per layer (NPCs do not count). Without it the map runs one context, exactly as before. On an instance map it fails the map (maps/crypt/map.json: "layerCap" is only for world maps; an instance map uses "maxPlayers"), as does a value below 1 ("layerCap" must be an integer >= 1). emptyTimeoutSec (default 300) is allowed with it: how long an empty extra layer lives on. Parsed in chthonic_map, so chthonic_mapbake and map tools check it too.
  • The base layer: instanceId 0, the map's ordinary context. It starts with the scripts, at startup, and never closes.
  • Extra layers are instance copies of the world map, made by the same machinery: each its own context (registry, AOI grid, Lua state with its own init, tile activation and NPC spawns) with a fresh instanceId from the instance counter, made and destroyed only at serial points. One with no players for the map's emptyTimeoutSec runs its systems' shutdown, loses its NPCs and is destroyed, as an empty instance copy is. Each logs layer created / layer destroyed {map, instance} (Operations).
  • Placement, for every arrival on the map (a login, a portal, a transfer from another map):
    1. the systems' layerFor(e, map), asked in system order: a live layer with room that one returns is joined;
    2. else the fullest live layer with room;
    3. else a new layer.
    Room is the player count at the last serial point plus the players already queued for that layer, as for an instance copy's maxPlayers. There is no rebalancing: players are never moved between layers by the server.
  • Within the map a transfer or portal keeps the player in its layer. chthonic.transfer(e, {map =, position =, layer = id}) moves to that layer if it is live with room; else it returns false and publishes instance.full {entity, map, layer}, nothing moves (Lua).
  • Never refused: when no new layer can be made (instance ids exhausted, or entity ids low), the player joins the fullest layer over its cap and no new layer: overfilling the fullest is logged (warn). A login or a transfer onto a world map is never refused because of layers.
  • NPCs do not count towards the cap and never open a layer: an NPC transferred or chthonic.created onto the map from another goes to the base layer (or the live layer a layer = names). A layer's own NPCs come from its spawn files.
  • Threads: layers spread players over contexts, but with MAP_THREADS=1 the contexts still update one after another. Measured (2000 bots, layerCap 500, 4 layers): tick p99 about 33 ms at MAP_THREADS=1, about 12 ms at MAP_THREADS=4. On a layered map set MAP_THREADS to about the expected layer count (Threading).
  • Relog: characters.instance_id holds the layer, as for an instance copy. On login the saved layer is rejoined if it is live with room; else (full, closed, or a previous run's) placement, at the saved position (saved layer not joinable; placing as a new arrival, logged). Rows with instance_id 0 go straight to placement. At a login there is no entity yet: the base layer's layerFor is asked with e nil.
  • Chat: /say, yell and emote reach players in view in the same layer only (each layer has its own registry and grid). Zone chat is per map id, so it spans every layer, unchanged (Chat).
  • Lua: chthonic.map.instance() in a layer is {id, map, layer = true, base} (base: id 0). A chthonic.world.post to the map reaches every layer's bus.
  • Admin: layers are listed in the admin port's instance list (map, instanceId, players, NPCs, empty timer; no key).
  • Load test: LAYER_CAP=500 tests/load.sh applies layerCap to START_MAP for one run (Tests).

Tile activation

A tile is near a player when it is at most ACTIVATION_TILES (default 1: a 3×3 block) tiles from the player's tile, counted the long way round (Chebyshev: max(|dx|, |dz|)), on the player's map. Like AzerothCore's grids:

  • Loading: the first time a tile is near any player, its spawn file entries are spawned. The tile then stays loaded for the life of the process: leaving it never despawns anything, and coming back spawns nothing twice. With no player online a start spawns no spawn-file NPC; the files are still all parsed and checked at startup, and a bad one still refuses the start. A login loads (and spawns) at once, so onEnter already sees the NPCs around the character; a move or transfer onto a new tile loads it for the next tick's spawner.
  • Sleep: an NPC (spawn file or chthonic.create) whose tile is near no player is asleep: Lua systems do not see it in chthonic.query, so it does not patrol and its timers in Lua do not run.
  • When: only when a player or an NPC changes tile or map (a move, a transfer, a login, a logout, a creation), never per tick for those that stay put. Keyed by (map, tile).
  • Visibility: unchanged. The view radius (AOI_VIEW_RADIUS, 128 m) is inside the 3×3 block whenever it is at most 256 m, so an NPC a player can see is always awake. A larger radius needs ACTIVATION_TILES of at least radius / 256 (rounded up), or a far NPC in view stands still until a player comes nearer.
  • Not unloaded: tiles never unload; ground, navmesh and objects are loaded for every tile at startup as before.

Ground

The server has no physics engine; it knows the ground from the same heightmaps the client stands on.

  • Loading: at startup, each owned tile's heights/<tx>_<tz>.r16 (tried first) or .png is decoded with chthonic_map's decode_heights. A tile without a file is flat at the map's heightMin (0 without heightRange). A file that fails to decode refuses the start (maps/hills/heights/0_0.png: png: 8-bit with 1 channel(s), need 16-bit grayscale).
  • Height: Maps::ground(map, x, z) is chthonic_map's ground_at: the triangle under the point, the same triangles as the client's Jolt heightfield, so client and server agree to within float rounding. Off the map's tiles it is empty.
  • Player moves: after the speed check, against the ground under the new position:
    • more than MOVE_GROUND_TOLERANCE (0.5 m) below it: accepted and lifted onto it;
    • more than MOVE_MAX_AIR (6 m) above it and not lower than the last position: rejected (Correction), so no flying or hovering;
    • lower than the last position: accepted, however high (falling).
  • Placement: NPCs always stand on the ground (chthonic.create, spawn files and chthonic.set of Transform ignore y). Transfers and portals put players and NPCs on the ground at the destination. A character saved under the ground (the heights changed since) enters on it.
  • Lua: chthonic.map.ground(map, x, z) is the height there, or nil off the map.

Objects

Map objects are what a map places on its tiles besides the ground: grass and flowers, rocks and trees, a shrine a player can use. A map editor authors them; map/objects.h (part of chthonic_map) parses both files for the server, chthonic_mapbake and any client or tool linking it.

TypeClientServer
visualthe prefab, no collisionnothing: never in a server file
obstaclethe prefab and a static Jolt body from shapeits shape is cut out of the navmesh
interactableas an obstacle; activating it sends Interact{id}as an obstacle, plus its .server/interactables entry: an Interact in range publishes its event

objects/<tx>_<tz>.json (shipped with the game) lists every object of the tile; an object belongs to the tile its pos is in:

{ "version": 1, "objects": [
  {"type": "visual", "prefab": "prefabs/grass.prefab", "pos": [120.5, 5.2, 131.0], "yaw": 2.4, "scale": 0.9},
  {"type": "obstacle", "prefab": "prefabs/rock.prefab", "pos": [141, 6.1, 108], "yaw": 0.3,
   "shape": {"cylinder": {"radius": 1.2, "height": 1.4}}},
  {"type": "interactable", "prefab": "prefabs/shrine.prefab", "pos": [118, 6.4, 140], "yaw": 0.4, "id": 1,
   "name": "Meadow Shrine", "shape": {"box": {"halfExtents": [1.2, 1.25, 1.2]}}} ] }
  • Every object: type, prefab (a project-relative .prefab), pos [x, y, z] on the tile; optional yaw (radians about +y, like heading: 0 faces +z, default 0) and scale (uniform, > 0, default 1; it scales the prefab only).
  • Shapes (obstacles and interactables must have one; a visual's is not read): {"box": {"halfExtents": [x, y, z]}}, turned by yaw, or an upright {"cylinder": {"radius": r, "height": h}}, every number > 0, in metres. A shape stands on pos (its base at pos.y) and is not scaled with the prefab, so the collision and the navmesh cut are exactly what the file says, whatever the prefab looks like.
  • Interactables also carry id (1-4294967295, unique on the map): what the client sends in Interact. name is optional, for the game's prompts (chthonic.nearestInteractable).
  • .server/interactables/<tx>_<tz>.json (server only, never packaged: the build skips dot-folders) has one entry per interactable of the tile, with what only the server needs:
{ "version": 1, "interactables": [
  {"id": 1, "pos": [118, 6.4, 140], "yaw": 0.4, "shape": {"box": {"halfExtents": [1.2, 1.25, 1.2]}},
   "range": 3, "event": "shrine.activated", "name": "Meadow Shrine",
   "data": {"message": "The shrine hums softly. You feel refreshed."}} ] }
  • id, pos (on the tile), shape and event (a non-empty event name, at most 255 bytes) are required; yaw, range (metres, > 0, default 3), data (a JSON object, at most 31 deep so the event payload stays within the bus's 32) and name are optional. The Map Builder writes pos, yaw, shape and name from the object and keeps the rest.
  • Range is the horizontal distance from the player's position to the shape's edge (0 inside it): map::footprint_distance; a client linking chthonic_map can use the same function to check range before it sends Interact.
  • Unknown keys are ignored in both files, so tools may keep their own.
  • Startup: the server loads the interactables files of its owned tiles (Maps::owns). A bad file name, a file for a tile not on the map, bad JSON, a bad entry, an id used twice on the map or bad data refuses the start with the file and the problem (maps/hills/.server/interactables/0_1.json: interactable 1: "range" must be a number > 0 (metres)).
  • Interact: a player's Interact{objectId} (protocol) is checked on the next tick: the id must be an interactable of the player's current map, and the player within its range. Then its event is published on the server bus as {entity, map, object, data} (data absent if the file has none; Events). An unknown id, another map's object or a player out of range publishes nothing and logs interact rejected at debug level (reason not on this map or out of range). There is no reply message: the game's Lua answers if it wants to. Interact counts toward the session's message rate limit like every message.
  • Blocking is the navmesh only: the server has no physics, so obstacles stop players and NPCs through the Navmesh cut (a move into one is off_mesh), and NPC paths go round them. The check's 0.5 m tolerance (made for the agentRadius shrink at cliffs) applies here too, so a player may graze up to about half a metre into a footprint's rim without a Correction; anything deeper is corrected (a 1.2 m rock accepts its player down to about 1 m from its centre). Clients block at the shape itself. Visuals never reach the server.
  • Bad client entries: the game client logs each bad entry or missing prefab with the file and skips it, keeping the rest. chthonic_mapbake refuses any bad entry.

Navmesh

The ground says how high a player is, not whether they could have walked there. A map can carry a baked navmesh (Recast/Detour) of where its agents can walk; the server checks player moves against it and NPCs path on it.

  • Baking: chthonic_mapbake lints a map and bakes its navtiles: see the Map Bake docs.

  • Obstacles: the bake reads objects/ and cuts every obstacle's and interactable's shape out of the walkable area (Recast area marking: rcMarkConvexPolyArea for a box's turned footprint, rcMarkCylinderArea for a cylinder), before the agentRadius erosion, so the mesh keeps that clearance round each one as it does round a cliff. A tile's bake includes its neighbours' objects that reach over its border. The whole column under a footprint is cut, whatever the shape's height. Visuals are ignored. A player can then not stand inside one (off_mesh, Correction), and chthonic.map.path goes round them. After adding, moving or removing a blocking object, re-bake.

  • Navtile format: a 12-byte little-endian header, {'KNAV', u32 version (1), u32 Detour DT_NAVMESH_VERSION (7)}, then the Detour tile from dtCreateNavMeshData for tile (tx, tz) (map/navtile.h).

  • Loading: at startup, each owned tile's navtile goes into one dtNavMesh per map (server/world/nav.cpp, the only file that includes Detour), sized for the map's declared tiles. A bad magic, an unknown navtile or Detour version, a tile baked for another tile, or too many polygons refuses the start with the file and the reason (maps/hills/.server/nav/0_0.navtile: navtile version 99, this server reads 1 (rebake with chthonic_mapbake)). A map without navtiles has no navmesh and keeps the Ground rules only.
  • Player moves: with MOVE_NAV_CHECK=1 (default), on a map with a navmesh, a move must end within 0.5 m across (the bake's agentRadius shrink at walkable edges) and MOVE_MAX_AIR up or down of a navmesh polygon. Otherwise the verdict is off_mesh and the client gets Correction at once, spending no move budget: walking up a cliff face or onto a slope steeper than maxSlopeDeg is snapped back. No grace period, so a player cannot drop off a cliff face either.
  • NPC paths: chthonic.map.path(map, from, to) ({x, y, z} tables) is the straight path along the navmesh: a list of {x, y, z} points from from snapped onto the mesh to to snapped onto it, with the corners between. It is nil when the map has no navmesh, either end is more than 2 m across (or 4 m up or down) from it, or to cannot be reached. The sample systems/npcs.lua walks these corners between a patrol's points, so the hills' Sentry goes round the mesa its route crosses.
  • Limits: Detour's poly refs are 32-bit here: tile bits + polygon bits <= 22, so the polygons a tile may have shrink as the map grows (map::max_navtile_polys): 65,536 at 8 x 8, 16,384 at 16 x 16, 4,096 at 32 x 32 and 1,024 at 64 x 64. Generated relief at 0.5 m cells peaks at 358-419 polygons a tile (2.9x headroom at 64 x 64). chthonic_mapbake fails on a tile over the limit, naming its polygons, the limit and the map's tile count, before the rest bakes; a navtile over it (baked for a smaller map) refuses the start. DT_POLYREF64 (Detour rebuilt, not needed so far) lifts it. Paths are capped by kMaxNodes 4096, kMaxPathPolys 1024 and kMaxPathPoints 256 (nav.cpp): a path across much of a big map can come back nil. No dynamic obstacles (an object that stops blocking, such as an opened door) or off-mesh links (jumps, ladders) in the bake, and the client does no pathing.
  • Sample: the sample maps' hills (in MAPS_DIR) has a mesa (x 170-200, z 316-346, 25 m flat top, 81 degree walls) and the Sentry (.server/spawns/0_1.json) patrolling from (150, 331) to (215, 331), straight through it and through a 3 m obstacle crate at (160, 331) (objects/0_1.json). Its other fixtures: a visual crate at (248, 244), an obstacle crate at (266, 248) and interactable 1 "Test Shrine" at (250, 266) (event test.shrine). Its baked navtiles are in .server/nav/; ctest mapbake_cli fails if they no longer match a fresh bake.
