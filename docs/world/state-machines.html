State machines

Server Lua and server C++ can drive finite state machines with the same definition files and rules as the game client. This page covers the file format, validation, ctx, the transition rules, and the chthonic.fsm API as the server runs them. A game's fsms/ folder can be shared with the server like components/. The code lives in server/lua/state_machines.* and server/lua/lua_state_machines.*.

  • Where they run: every map context and the realm context load fsms/. The game machines run in the realm context only; each map's chthonic.fsm reads a copy of their states (refreshed at every serial point), and a change of one from a map is checked against that copy (a denial warns and returns false there, as before), returns true and is applied in the realm at the next serial point, where its callbacks run. The same change asked by several maps at one serial point is applied once. Character and NPC machines run in the context of the map their entity is on, and move along with it (the StateMachine component keeps its current state).
  • Definitions: LUA_ROOT/fsms/**/*.lua, one machine per file, loaded once per context before the systems' init. Each file runs in its own sandboxed environment with the full read-only chthonic API. chthonic.log from a callback is prefixed with the definition path (fsms/door.lua: ...). A missing fsms/ folder means no machines.
  • Game machines: GAME_STATE_MACHINES lists them by name. At startup, in the realm context and before any map's systems load (so an init already reads their state), each enters its initial state: enter runs with ctx.from = nil, and no fsm.changed is published. Game machines run for the server's lifetime; shutdown runs no exit.
  • Character and NPC machines: use the writable built-in StateMachine (machine, initialState) through chthonic.add, chthonic.set, chthonic.get, chthonic.has, chthonic.remove and chthonic.query.
    • chthonic.add alone leaves machine empty: there is no machine yet, and chthonic.fsm.* on that character raises.
    • Setting machine enters that machine's initial state at once. That is initialState if it names a state, otherwise the definition's initial, with a warning. from is nil and no event is published.
    • Changing machine enters the new machine's initial state, with no exit of the old one. Changing only initialState does nothing. A machine with no valid definition is logged once.
    • Removal, logout and graceful shutdown just drop the machine, with no exit.
    • The typical use is a system's onEnter adding and setting it (see the sample).
  • Not persisted, not replicated: StateMachine and the current state never reach MySQL (the components column) or clients. A character starts its machine again from the initial state on every login. To tell clients about a transition, send it from enter (chthonic.sendTo / sendNearby).
  • Events: fsm.changed {machine, entity, from, to} goes on the event bus of the entity's map (the publisher set to the definition path), delivered at the normal drain (see Events), so a transition made in update reaches subscribers in the same tick. A game machine's (entity null) goes on the realm's bus and is passed on to every map's bus at the start of the next tick: one changed by C++ between ticks reaches the maps' subscribers in that tick, one a map asked for at the end of the tick after it was applied.
  • Callback errors: an error in enter or exit is logged as State machine fsms/door.lua: enter "open" failed: fsms/door.lua:5: ... with a traceback. The transition still commits and the machine stays usable; no system is disabled. A callback runs under the 2 s script budget of whatever entered Lua. When a system's chthonic.fsm.change of a character or NPC machine triggers a runaway callback, the callback is stopped and logged, and then that system is disabled too, because they share one budget. A game machine's callback runs in the realm, under the realm's own budget: stopped and logged, and no system is disabled.
  • Misuse: every bad chthonic.fsm.* argument raises at the calling line, which a system callback treats like any other error (the system is disabled). An unknown state name passed to change is a denial (false and a warning).
  • Startup: a rejected fsms/ file or a GAME_STATE_MACHINES name with no valid definition refuses the start, like any other Lua error (one Lua error line each, startup failed: Lua, exit status 1). That also applies when LUA_ROOT is missing and GAME_STATE_MACHINES is set.
  • C++: World::realm_fsm() (the game machines) and World::fsm(map) (that map's characters and NPCs by wire id; World::fsm(): START_MAP's) are lua::StateMachines (also Runtime::fsm()), with state, change, canChange and states. They apply the same rules, events and logging as chthonic.fsm, and a bad target throws std::invalid_argument.
  • Not on the server: hot reload, scenes and chthonic.loadScene, editor panels.
std::string phase = world.realm_fsm().state("zone_cycle");              // a game machine by name
bool moved = world.fsm(world.map_of(e)).change(lua::EntityId{7}, "moving"); // a character's machine by wire id
